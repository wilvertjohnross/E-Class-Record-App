E-CLASS RECORD APP — SIGNED DEVELOPMENT UPDATE FORMAT
Bootstrap security baseline: v1.0.20

PURPOSE
Ordinary runtime/UI/template iterations can still be delivered as *.ecrupdate files,
but v1.0.20+ accepts only packages signed by the trusted Ed25519 development key.
The private key is kept outside the application and is never distributed with builds.

PACKAGE FORMAT
.ecrupdate is ZIP-compatible:
  manifest.json
  payload/
    app/index.html
    app/app.js
    main-extension.js
    templates/...

manifest.json includes:
  format: 1
  appId: ph.edu.eclassrecord.gs.sf9
  productName: E-Class Record App with GS and SF9
  version: semantic version newer than the effective version
  minBootstrapVersion: 1.0.20 or newer
  files: exact SHA-256 map for every payload file
  signature.algorithm: ed25519
  signature.keyId: ecr-dev-2026-01
  signature.value: Base64 Ed25519 signature over the canonical manifest fields

VALIDATION
The updater verifies package size, manifest size, entry count, safe ZIP paths,
per-entry size, total uncompressed size, exact signed file list, SHA-256 hashes,
application identity, version compatibility, and Ed25519 signature. Staged files
are re-hashed and the signed manifest is reverified before activation/loading.

CREATE A SIGNED UPDATE
Keep the private key outside the project folder. On Windows:
  set ECLASS_UPDATE_SIGNING_KEY=C:\secure\ECR_UPDATE_SIGNING_PRIVATE_KEY.pem
  node tools\make-thread-update.js 1.0.21 path\to\payload update.ecrupdate

IMPORTANT
- Future update payloads should be self-contained snapshots of all runtime files they need.
- Bootstrap/preload/native dependency changes still require a full installer.
- Do not distribute the private signing key.
- This remains a private development channel; eventual schoolwide releases should also use
  normal Windows publisher/code signing and a trusted hosted release channel.
